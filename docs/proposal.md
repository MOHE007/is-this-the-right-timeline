# 知乎黑客松游戏项目策划书

## 这真的是对的时间线吗

三章叙事动作游戏 Web Demo 方案

| 项目字段 | 方案定义 |
| --- | --- |
| 参赛赛道 | 跨次元游乐场  社区 × 游戏 |
| 推荐引擎 | Godot 4.x  GDScript  Web 导出 |
| 首个交付物 | 三分钟可演示的垂直切片 |
| 平台目标 | 桌面浏览器公网 Demo |
| 方案版本 | V1.0  2026年9月 |

**决策摘要**

本项目建议改用 Godot 4.x 重做，不再以手写 HTML Canvas 作为主游戏技术。Godot 能在同一套场景和脚本体系中承载第一章的界面叙事、第二章的 2D 动作和第三章的 3D 射击，并可导出到浏览器。为了控制比赛风险，首轮不追求三章完整内容，而是交付一个包含完整第一章和两段战斗体验的垂直切片。

项目要让评委记住的不是“我们用了 AI 生成内容”，而是“玩家进入自己没读完的知乎问题，并在不同玩法中完成一次从逃避到行动的成长”。

## 项目目标与成功标准

游戏讲述一名临近毕业的大四学生。主角因未来选择而迷茫，沉迷知乎上的历史与战争文章，随后穿越进文章构成的世界。刘看山作为系统同行者，引导主角穿过三个文中小世界，直到主角理解：问题不会因为逃避而消失，答案需要阅读、判断和行动共同完成。

### 项目目标

- 让玩家在五分钟内理解主线、体验一次关键选择，并感受到玩法从阅读转为行动。
- 用三种玩法表达同一个主题：第一章判断，第二章执行，第三章承担后果。
- 让刘看山提供可用的提示与回答，而不是跳出游戏的聊天机器人。
- 交付一个可公网访问、可重复演示、即使 AI 服务暂时不可用也能通关的 Web Demo。

### 成功标准

| 维度 | 通过条件 |
| --- | --- |
| 叙事 | 玩家能复述主角为什么穿越、刘看山做什么、最后为什么醒来。 |
| 第一章 | 至少三条分支、三种结局，线索会改变可见选项。 |
| 第二章 | 玩家能完成移动、跳跃、攻击、拾取和一次明确目标。 |
| 第三章 | 玩家能完成移动、视角控制、瞄准、射击和一轮敌袭。 |
| AI | 玩家主动提问时能获得与当前章节相关的回答；离线时有稳定兜底。 |
| Web | 首屏能在桌面浏览器打开，资源加载有进度提示，演示不依赖本地文件协议。 |

## 引擎选择与技术决策

推荐 Godot 4.x，脚本使用 GDScript。Godot 官方文档支持将项目导出为 HTML5，并说明 Web 导出基于 WebAssembly 与 WebGL 2.0；Godot 4.3 起支持单线程 Web 导出，减少对跨域隔离响应头的依赖。Godot 4 的 C# 项目目前不能导出到 Web，因此本项目不使用 C#。

| 方案 | 适合之处 | 主要问题 | 本项目判断 |
| --- | --- | --- | --- |
| Godot 4.x | 同一项目支持 2D、3D、场景、动画、物理和 Web 导出；开源 MIT 许可；GDScript 上手快。 | Web 端仍需控制包体、纹理、音频和 3D 场景规模；不能用 C# 做 Web 导出。 | 推荐。最适合本项目的平衡点。 |
| Unity | 3D 工具链成熟，资源、动画、输入、调试体系完整。 | Web 端更依赖桌面浏览器和内存，构建包体与加载体验需要更严格的优化；团队需要承担更重的工程配置。 | 备选。若团队已有 Unity 经验且第三章是绝对主角。 |
| Phaser | 专门面向浏览器，2D 迭代快，资源小，前端部署直接。 | 官方定位是 2D 框架，不内置 3D 渲染和 3D 物理；第三章需要额外技术栈。 | 不推荐作为唯一引擎。可用于纯 2D 版本。 |

### 为什么不继续使用手写 Canvas

当前 Demo 的问题不是画面不够华丽，而是缺少真正的游戏工程结构。手写 Canvas 可以快速画出一个场景，但场景切换、碰撞、动画、输入状态、摄像机、资源管理、存档和调试都需要自行维护。三章玩法差异一旦扩大，代码会把精力从“设计玩家体验”拖向“修补基础系统”。引擎的价值正是把这些基础能力变成可复用的项目结构。

## 核心玩法与三章结构

三章不是三个互不相关的小游戏。它们应共享一个玩家状态、一个线索系统和一个刘看山系统。章节玩法的变化服务于主角的心理变化：先阅读和判断，再进入行动，最后在混乱中保护重要的东西。

| 章节 | 玩家体验 | 关键交互 | 叙事任务 | 垂直切片范围 |
| --- | --- | --- | --- | --- |
| 第一章 靖康前夜 | 选择与线索类文字游戏 | 查阅军报、组合线索、做出多次选择 | 主角第一次意识到“改变历史”需要承担新的问题 | 完整章节，3 个结局，6 至 8 个节点 |
| 第二章 戚家军神威 | 2D 横版动作闯关 | A/D 移动，W 跳跃，鼠标左键攻击，右键查看，F 拾取和操控 | 主角从旁观者变成执行者 | 一段 3 至 5 分钟战斗走廊，3 面军旗，1 个营门目标 |
| 第三章 淞沪回声 | 3D 第一人称射击与探索 | WASD 移动，鼠标转向，左键射击，右键瞄准 | 主角在现实重量最强的场景中选择守护 | 一个小型 3D 防守场景，1 轮敌袭，1 个回家信号 |

### 第一章的多结局设计

第一章负责建立作品辨识度，必须做完整。玩家先从文章残页、军报旧印和河图中收集信息，再在城门前选择“接受时间线”“尝试改写”或“补全问题”。三个结局不以简单的好坏排序，而是分别表达见证、冲动和理解。只有收齐线索，玩家才会看见“真结局”，从而自然回扣知乎的阅读与求知。

**时间线修正**：本章发生在 1122 年，主角 2 岁；岳飞约 20 年后于 1142 年去世。1122 年仍属于北宋末年，尚未进入南宋，因此章节标题统一使用“靖康前夜”，不再使用“南宋意难平”。

### 通关彩蛋

通关后出现：刚才打的那些不是游戏，都是你在知乎上没读完的问题。最后一句收束为：只要有问题，就有回答。

## 刘看山与 AI 设计

刘看山不是一个永远正确的解说员。它的职责是帮助玩家继续思考和行动，因此回答需要有边界：提供背景、解释规则、提醒线索、回应玩家状态，但不直接替玩家选择，也不把历史人物简化成单一答案。

| 能力 | 游戏内表现 | 离线兜底 | 线上增强 |
| --- | --- | --- | --- |
| 提醒 | 在节点、战斗和迷路状态下出现一句短提示。 | 由章节状态机触发固定提示。 | 根据玩家当前线索和行为生成更贴合的提醒。 |
| 问答 | 玩家在侧边栏输入问题，刘看山用一句到三句回答。 | 本地知识库覆盖历史、操作和当前目标。 | 通过服务端代理调用知乎直答，密钥不进入浏览器。 |
| 解释 | 玩家查看物件、军报和文章残页时得到上下文说明。 | 每个关键物件有结构化说明。 | 可补充知乎文章来源和相关问题链接。 |
| 叙事 | 回答内容会影响下一条提示和日志，不改变核心关卡状态。 | 使用预设角色语气。 | 根据玩家提问形成个性化的旅途记录。 |

AI 接入采用“游戏客户端、游戏服务端、知乎能力适配器”三层结构。浏览器只提交玩家问题和章节上下文，服务端负责鉴权、限流、超时和兜底。这样即使公网 AI 暂时不可用，玩家仍能通过本地答案完成演示。

## 视觉与声音方向

三章的美术差异要服务于“文章世界逐步变得真实”，而不是为了展示技术而切换风格。建议统一使用低饱和墨色、纸张纹理和金色线索标记，让不同玩法仍属于同一部作品。

| 章节 | 画面语言 | 动效与声音 |
| --- | --- | --- |
| 第一章 | 纸面、墨线、残页、印章和局部留白。选择按钮像翻页批注，线索像被压进文章的纸片。 | 翻页、墨水晕开、远处风声和低音弦乐。 |
| 第二章 | 皮影轮廓、横向卷轴、木刻纹理和有限色彩。敌我轮廓要一眼可辨。 | 刀枪、旗帜、脚步和战鼓；命中反馈要短而清楚。 |
| 第三章 | 低多边形 3D、雾、远处信号灯和克制的红色警示。减少复杂建筑，保证 Web 性能。 | 风声、远处炮火、呼吸和信号灯提示音；射击声避免连续轰鸣。 |

## 技术架构与网站交付

| 模块 | 建议实现 |
| --- | --- |
| 引擎 | Godot 4.x，GDScript；项目按章节拆分为独立场景。 |
| 场景结构 | Boot、Title、Chapter01、Chapter02、Chapter03、Ending、UI 等场景；主流程由 GameState 单例管理。 |
| 数据结构 | 线索、选择、结局、对白和问答知识使用 Resource 或 JSON 配置，不把内容硬编码在角色脚本中。 |
| 输入系统 | 使用 Godot Input Map，统一定义移动、跳跃、攻击、查看、拾取、瞄准和提问。 |
| 存档 | 第一阶段使用浏览器本地存储保存章节和结局；不做账号依赖。 |
| Web 导出 | 优先使用 Godot 单线程 Web 导出，控制首包和纹理尺寸；使用自定义 HTML 壳承载知乎品牌入口和加载状态。 |
| AI 服务 | 同源 HTTPS API 代理；服务端保存凭证，客户端只接收回答和脱敏状态。 |
| 公网交付 | 构建产物部署到可提供静态文件和 API 代理的平台；上线前用桌面 Chrome、Edge、Safari 各跑一次通关路径。 |

### 网站首屏流程

- 首屏说明一句话玩法和推荐操作，点击开始后先加载第一章，不让玩家在菜单中迷路。
- 右上角固定显示章节、线索数、刘看山状态和静音按钮。
- 每次章节切换只保留一条目标，避免把策划信息全部塞给玩家。
- 演示模式提供“从章节开始”入口，评委可跳过已完成内容，但默认路径仍从第一章开始。

## 开发阶段与交付节奏

以下节奏用于控制风险，不代表必须在固定天数内完成。每个阶段都要有可运行版本，不能等到最后才把三章拼在一起。

| 阶段 | 主要工作 | 阶段验收 |
| --- | --- | --- |
| 阶段一 设计锁定 | 确定第一章节点图、三章输入、玩家状态、AI 提示边界和素材风格。 | 能用纸面流程走通三种结局；所有交互都有明确输入。 |
| 阶段二 第一章垂直切片 | 完成 UI 叙事、线索、选择、日志、结局和刘看山提示。 | 评委可在 3 分钟内走出至少一个结局，第二次游玩能走不同分支。 |
| 阶段三 第二章动作样片 | 完成横版玩家控制、敌人、攻击、拾取、目标和一次转场。 | 不看说明也能理解如何移动、攻击和拿旗。 |
| 阶段四 第三章空间样片 | 完成 3D 相机、移动、瞄准、射击、敌袭和信号灯目标。 | 玩家能在第一分钟内找到视角和目标，场景不因 Web 性能卡顿。 |
| 阶段五 网站与 AI | 接入加载页、错误兜底、问答适配器、统计和公网部署。 | 断开 AI 服务仍可通关；线上链接能从首屏走到结尾。 |
| 阶段六 演示打磨 | 统一字体、音效、转场、操作提示、录屏和测试说明。 | 形成一条 3 分钟演示路径和一条完整体验路径。 |

## 风险与取舍

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 三种玩法都做得过大 | 每一章都像半成品，玩家记不住主线。 | 第一章完整，后两章做短而有反馈的垂直切片；先保证转场和主题成立。 |
| Web 3D 包体过大 | 首屏等待长，评委可能在加载前离开。 | 低多边形场景、压缩纹理、短音频、单线程 Web 导出；把第三章控制在一个小型场景。 |
| AI 延迟或失败 | 玩家卡在问答界面，演示不可控。 | 本地答案库、超时和错误提示三层兜底；AI 只增强体验，不决定关卡能否通关。 |
| 历史表达被误读 | 战争章节变成单纯射击，削弱项目主题。 | 使用普通人的任务和守护目标，避免把历史人物写成单一标签；在物件和对话中保留问题背景。 |
| 素材版权和生成一致性 | 画面风格不统一或无法提交。 | 建立素材清单和来源记录；AI 生成素材只作为草图或经人工筛选后使用，保留可替换源文件。 |
| 知乎能力接入拖慢开发 | 开放平台配置问题占用核心开发时间。 | 先做无账号基础版；登录和知乎直答作为独立服务层，待公网部署后再接入。 |

## 最终建议

现在最适合的路线是 Godot 4.x + GDScript + 单线程 Web 导出。先用 Godot 做出一个质量足够高的第一章，再用两段短战斗证明第二章和第三章确实存在。这样既能回应赛道的“社区 × 游戏”，也能避免被三套玩法的工程成本拖垮。

下一步不应直接开始堆素材，而应先完成第一章的节点图、输入表和一张视觉风格板。第一章通过后，再把同一套 GameState、刘看山和网站壳复用到两个动作章节。
