# 《这真的是对的时间线吗？》产品说明计划书

> 初审重点：项目创作思路、技术方案，以及与知乎社区场景的适配价值。

## 一、项目概述

《这真的是对的时间线吗？》是一款**「知乎内容 × 叙事游戏」**的跨次元作品。玩家扮演一名因毕业选择而迷茫的大四学生，在阅读一篇没读完的知乎历史文章时，被拉进文章构成的时间线。在刘看山的陪伴下，玩家穿越 1122 年北宋末年、南宋军镇与 1161 年，通过**观察、调查、提问、验证**，反复面对同一个问题：

> 如果已经知道一个人的结局，我们是否真的有能力改变它？

**当前交付物**为第一章「南宋意难平」的完整垂直切片，已在三条通道发布：

| 通道 | 地址 | 状态 |
| --- | --- | --- |
| 网页版（免安装） | `https://mohe007.github.io/is-this-the-right-timeline/` | 可玩，冷启动约 20 秒 / 缓存命中约 5 秒 |
| macOS 桌面版 | GitHub Release `demo2-ch1-v0.2.2` | 通用二进制（Apple Silicon + Intel），解压即玩 |
| Windows 桌面版 | GitHub Release `demo2-ch1-v0.2.2` | 64 位单文件，免安装 |

仓库：`https://github.com/MOHE007/is-this-the-right-timeline`（MIT License）

## 二、创作思路

### 1. 把知乎的「有问题，就有回答」做成可玩的机制

知乎内容的核心不是单向讲述，而是**提问、回答、比较、追问**。本项目没有把这套文化当作标语，而是逐层翻译成玩家行为：

| 知乎行为 | 游戏机制 |
| --- | --- |
| 提出问题 | 玩家进入文章时面对一个未完成的问题 |
| 阅读资料 | 调查驿站家书、渡口证言、军镇军书、路线图 |
| 追问求证 | 向刘看山提问，拿到「事实 / 背景 / 反问」三段回答 |
| 比较判断 | 决定相信谁、先查什么、是否介入 |
| 给出回答 | 结局是玩家用行动写下的答案，不是系统宣布的对错 |

**关键设计：求知是有成本的。** 刘看山的验证提问预算只有 **4 次**，缺少对应道具时会回答「信息不足」，**但提问次数照样消耗**。这直接对应知乎的真实体验——问题问得不对，时间就白花了。玩家因此学会"先观察，再提问"。

### 2. 用普通人的视角补足英雄叙事

第一章以 1140 年班师诏、1141 年兵权与和议、1142 年岳飞之死为历史支点，但**玩家不扮演英雄，也不能靠集齐道具改写结局**。

玩家调查的是：一封没有官印的家书、一位迁徙者的原话、一份缺页军书、一块传令牌。设计意图是：

> 大事件提供时代背景，普通人承担具体代价。

即便玩家成功把预警送出去，结局也不是「岳飞活下来了」，而是**「你改变了消息抵达的速度，没有改变朝廷要一个答案的心」**。这既守住历史严肃性，也避免把悲剧做成爽文。

### 3. 拿到道具 ≠ 理解——三层证据系统

本项目把「知道」和「理解」拆成三段，这是第一章的核心玩法设计：

| 层级 | 玩家动作 | 含义 |
| --- | --- | --- |
| **物证** | 点击拾取家书 / 军书 / 路线图 / 证言 | 证明事情发生过 |
| **行动资格** | 找到令牌、问清谁能执行 | 允许尝试介入 |
| **刘看山验证** | 带着道具向刘看山提问 | 把"看见"变成"理解" |

**只有三层齐备，特殊结局才会解锁。** 拿到军书但没问过"谁有能力执行"，玩家依然进不了完整的介入链——这正是知乎「收藏了不等于读懂了」的游戏化表达。

### 4. 漏掉线索不 Game Over，但要付出明确代价

探索允许遗漏。漏拿关键物时，游戏立刻给出**因果反馈**而不是惩罚：

- 「你拿到了军书，但不知道它该交给谁。」
- 「路线图被水浸过，方向存在，距离没有。」
- 「刘看山看见了证言，却无法替你证明它。」

玩家可以带着缺口继续走「历史轨迹」，或走一条明确说明缺口的「普通收束」。**失败被写成后果，而不是关卡重置。**

### 5. 三章对应三种认知递进

| 章节 | 玩法 | 认知主题 |
| --- | --- | --- |
| 第一章（已交付）| 文字调查、线索验证、多结局 | 我应该相信什么？ |
| 第二章《戚家军》 | 横版动作、队伍协作 | 我能不能真正行动？ |
| 第三章《淞沪回声》 | 3D 探索、资源与守护 | 行动之后，我愿意承担什么？ |

三章不是三个小游戏，而是同一角色从「旁观」走向「判断、行动、承担」的连续过程。

## 四、AI 机制：刘看山不是外挂

刘看山是**游戏内同行角色**，也是本项目对知乎社区形象的功能化用法。

### 三档帮助，逐级降低门槛

| 档位 | 触发 | 作用 |
| --- | --- | --- |
| 提醒 | 玩家遗漏线索、长时间停留 | 指向下一步调查对象 |
| 回答 | 玩家主动提问 | 给出事实、背景、反问 |
| 救助 | 多次卡关 | 给出最小必要提示 |

### 回答结构固定为「事实 → 背景 → 反问」

> **事实**：1140 年班师诏已成事实；1141 年真正的链条是罢兵权、构陷、下狱与和议。
> **背景**：军书写得再快，也要有来源、路线、接收者和执行能力四个环节。
> **反问**：你想拦住的是一纸诏书，还是朝廷要一个答案的心？

**反问永远把判断权交回玩家。** 刘看山不替玩家选择，也不替玩家承担结局——这是与「AI 代打」式设计的分界线。

### 离线优先的可替换适配层

本地问答库保证**断网也能完整通关**；联网 AI 是体验增强，不是运行硬依赖：

```text
ask(question, chapter_context) -> { fact, context, counter_question } | insufficient | exhausted
```

## 五、技术方案

### 1. 引擎与发布矩阵

- **引擎**：Godot 4.3（`4.3.stable.official.77dcf97d8`），GDScript，GL Compatibility 渲染器
- **一份工程，三种导出**：Web（WebAssembly）、macOS 通用二进制、Windows 64 位
- **中文渲染**：内嵌 Noto Sans SC 子集，不依赖系统字体回退（浏览器端尤其关键）

### 2. 内容与运行时分层：人读 Markdown，机器读 JSON

| 载体 | 用途 |
| --- | --- |
| Markdown | 剧本、分镜、角色卡、线索卡、实现规格、史实审校 |
| JSON | 场景节点、对白、选项、状态变量、条件、效果、结局路由 |

第一章的 JSON 契约分三层：`state`（变量 / 条件 / 效果目录）、`content`（对白 / 选项 / 调查对象）、`manifest`（资源绑定 / 场景视觉 / 音频映射）。

### 3. 数据驱动运行时（不做硬编码）

运行时把契约当作**可执行语义**而非配置文本：

- **效果引擎**：`set` / `increment` / `decrement` / `append_unique` / 条件守卫 `guard`，支持 `effect:param` 参数替换
- **条件引擎**：`all` / `any` / `eq` / `gte` / `lte` / `contains`，命名条件递归求值
- **契约合并**：v01 基础 + v02 补丁按**键级合并**，未提及项保留，避免版本升级丢场景

**收益**：剧本、数值、分支调整不需要改代码；改文案不动结构，改结构不动美术。

### 4. 交付链路与性能工程

网页版最大的敌人是首屏等待。本项目做了四层优化，**首屏从约 12 分钟降到 20 秒**：

| 手段 | 效果 |
| --- | --- |
| 贴图按实际渲染尺寸重做（背景 1280×720、立绘 512×768） | 资源包 14.2MB → 7.9MB |
| 中文字体子集化（按全部文本用字 702 字符，覆盖校验 100%） | 字体 8.3MB → 173KB |
| 运行时未用资源排除出包（联络表图、评审截图） | 再省约 3MB |
| 静态资源走 CDN 快线路 + wasm 分片重组 + 部署后自动预热缓存 | 首屏 20 秒、缓存命中 5 秒 |

其中 wasm 分片方案解决了 CDN 单文件体积限制，由页面内的一段重组逻辑还原完整二进制——玩家无感，加载被拆成多个可并行的快请求。

### 5. 知乎开放平台接入（真实打通，非贴牌）

项目已独立部署 Node OAuth 服务，接入知乎开放平台账号体系：

- 授权链路：`/api/oauth/start` → 知乎授权页 → `/auth/callback` → 服务端换取 token
- 已接通 5 类账号接口：**我的创作 / 我的关注 / 收藏夹 / 收藏内容 / 近期收藏**
- 密钥全部存放于系统钥匙串与平台环境变量，不进仓库、不进日志
- 容器化部署（GitHub Actions 构建镜像 → 云平台运行），回调地址经环境变量注入

这使"知乎社区 × 游戏"不只是题材嫁接，而是**可扩展到账号级内容联动**的真实能力。

### 6. 工程质量与验证手段

| 手段 | 覆盖 |
| --- | --- |
| 五条路线无头冒烟测试 | 三结局 + 漏线索兜底 + 提问耗尽，5/5 通过 |
| 存档往返断言 | 场景 / beat / 信任 / 线索一致性 |
| 美术接入探针 | 逐场景背景与逐说话人立绘，14/14 场景通过 |
| 音频接入探针 | 逐场景 BGM/环境与 10 个交互音效，10/10 通过 |
| 契约静态校验 | 场景引用、条件、效果、资源绑定一致性 |
| 史实审校流程 | 1140 班师诏 / 1141 兵权与和议 / 1142 赐死三个时点经独立复核 |

## 六、适配知乎社区的场景价值

### 1. 让「阅读内容」变成「可参与的世界」

知乎内容通常以问题、回答、讨论展开。本项目把阅读转化为：**可进入的文章世界、可调查的证据空间、可追问的 AI 回答、可承担后果的选择**。它验证了一件事——知乎内容可以从图文形态进入互动叙事，而不损失其信息密度。

### 2. 把平台的问题文化做成机制，而不是装饰

项目保留并强化了知乎最核心的表达方式：从问题开始、鼓励追问、允许答案并存、用证据形成判断。**最有代表性的是"提问有成本"**：4 次验证预算 + 「信息不足」照样消耗。玩家在游戏里体验到的，正是知乎上"问对问题比问得多更重要"。

### 3. 刘看山从形象升级为「问题连接器」

刘看山在游戏中承担：理解复杂背景、把知识转成可行动线索、在卡关时降低门槛、**用反问保留玩家自己的判断空间**。它不是引导点击的吉祥物，而是内容与玩家之间的中介——这比让刘看山只做装饰角色，更贴近其社区定位。

### 4. 一套可复用的内容改造管线

第一章验证的 JSON 契约（场景 / 问答 / 线索 / 条件 / 结局）**与具体题材无关**。同一套引擎可以直接承载：

- 历史问题章节（已实现）
- 科普、社会议题互动故事
- 用户问题改编的短篇关卡
- 社区共创的多结局时间线

这意味着产品价值不止于一章剧情，而是**一套把知乎问题批量转成互动体验的管线**。

### 5. 天然具备分享与复盘属性

每个玩家的结局组合不同（介入 / 见证 / 收束），且会带着不同的缺口结束。这天然生成知乎式的二次讨论：

- 你选择介入还是旁观？
- 你认为哪条证据最重要？
- 改变历史是否一定代表更好的结果？
- 如果是你，会把预警交给谁？

结算画面还提供**两张可交互 3D 卡片**（岳飞 / 辛弃疾）作为可独立分享的内容载体，把游戏体验延伸成可传播的素材。

### 6. 内容可信度优先

历史题材最大的风险是失真。本项目把**史实审校**作为独立环节：由审校岗复核关键时点（1140 年班师诏、1141 年罢兵权与和议、1142 年赐死），并明确区分"史实"与"艺术留白"。这保证了作品在知乎社区**经得起追问**——这也是在知乎做内容的基本门槛。

## 八、项目价值总结

《这真的是对的时间线吗？》尝试回答一个具体的产品问题：

> 知乎上的一个问题，能不能从「被阅读的内容」变成「被亲自经历的世界」？

项目用**游戏**提供行动，用**刘看山**提供引导与反问，用**知乎的问题文化**提供叙事起点，再用**历史时间线与多结局**让玩家承担自己的判断。它不把文章做成游戏，而是让玩家在阅读、提问、调查和选择中，真正经历一次：

> 从知道问题，到愿意回答问题。

> 只要有问题，就有回答。
