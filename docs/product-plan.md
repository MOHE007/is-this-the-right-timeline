# 《这真的是对的时间线吗？》产品说明计划书

> 初审重点：项目创作思路、技术方案，以及与知乎社区场景的适配价值。

## 一、项目概述

《这真的是对的时间线吗？》是一款“社区内容 × 叙事游戏”的浏览器游戏。

玩家扮演一名因毕业和未来选择而迷茫的大四学生，在阅读一篇尚未读完的知乎历史文章时，意外进入文章构成的时间线。玩家将在刘看山的陪伴下，穿越 1122 年、南宋军镇以及后续历史场景，通过阅读、调查、提问和行动，重新理解一个核心问题：

> 如果已经知道一个人的结局，我们是否真的有能力改变它？

项目当前以第一章《靖康前夜》为主要 Demo，采用水墨叙事、线索调查和多结局设计，后续扩展为三章、三种玩法的完整作品。

## 二、创作思路

### 1. 把知乎的“问题意识”变成游戏机制

知乎内容的核心不是单纯讲故事，而是提出问题、寻找答案、比较观点。

本项目将这种内容结构转化为玩家行为：

- **问题**：玩家进入文章时先看到一个未完成的问题。
- **阅读**：通过文章残页、家书、军书、路线图和人物证言获取信息。
- **追问**：玩家可以向刘看山提问，获得事实、背景和反问。
- **判断**：玩家决定相信谁、帮助谁、是否介入时间线。
- **回答**：结局不是简单的成功或失败，而是玩家对问题做出的行动性回答。

玩家不是被动观看一段历史，而是在“阅读一篇知乎问题”的过程中，亲自承担判断结果。

### 2. 用普通人的视角补足英雄叙事

第一章围绕岳飞 1141 年被召回、1142 年结局展开，但玩家不会直接扮演英雄人物，也不会把历史简化为“找到关键道具即可改变结局”。

玩家需要调查：

- 驿站中的家书与送信路线
- 渡口迁徙者的证言和征发文书
- 军镇中的军书、权限和执行能力
- 召回消息的来源、路线、接收者与执行者

大事件提供时代背景，普通人承担具体代价。玩家最终理解：

> 知道历史结局，只是获得了信息；改变结果还需要消息、信任和执行能力同时成立。

### 3. 三章对应三种认知变化

| 章节 | 玩法 | 认知主题 |
| --- | --- | --- |
| 第一章《靖康前夜》 | 文字调查、线索拼图、多结局 | 我应该相信什么？ |
| 第二章《戚家军》 | 横版动作、队伍协作 | 我能不能真正行动？ |
| 第三章《淞沪回声》 | 3D 探索、资源与守护 | 行动之后，我愿意承担什么？ |

三章不是三个独立小游戏，而是同一个角色从“旁观和逃避”走向“判断、行动、承担”的连续过程。

## 三、第一章 Demo 设计

第一章时间线为：

> 1122 年 → 1127 年 → 1141 年 → 1142 年 → 1161 年

玩家以两岁婴儿身份进入 1122 年的北宋末年，在没有行动能力的情况下，先记住岳飞将在 1142 年离世。随着时间推进，玩家长大并调查驿站、渡口和军镇，逐渐建立四类信息：

1. 消息从哪里来
2. 消息经过什么路线
3. 谁能够接收消息
4. 谁拥有真正的执行能力

第一章使用 14 个运行时场景节点，并设置三种结局：

- `ending_canonical`：历史轨迹继续
- `ending_divergent`：时间线发生偏离，但产生新的军政压力
- `ending_truth`：玩家保存普通人证言，理解现场真相与后世叙述之间的差异

三种结局不做简单的“好 / 坏”排序，而是展示不同选择带来的代价。

## 四、AI 机制

刘看山在项目中不是外挂式聊天机器人，而是游戏内的同行角色。

### 三档帮助

| 档位 | 游戏表现 | 作用 |
| --- | --- | --- |
| **提醒** | 在玩家停留或遗漏线索时出现 | 指向下一步调查对象 |
| **回答** | 玩家主动提问 | 提供事实、背景和反问 |
| **救助** | 玩家连续失败或卡关 | 给出最小必要提示 |

回答结构固定为：

> 事实 → 背景 → 反问

例如：

- 事实：岳飞于 1142 年离世。
- 背景：召回并不是一个单独事件，而是一条政令和执行链。
- 反问：你准备先查消息来源，还是先找能执行它的人？

AI 不直接替玩家选择，也不替玩家承担结局。

### 技术实现

项目采用可替换的 AI 适配层：

```text
ask(question, context)
```

- 浏览器端只提交当前问题和章节上下文。
- 服务端负责调用外部 AI 能力、超时处理和安全控制。
- 本地问答库作为离线兜底。
- 即使联网服务不可用，玩家仍可完成 Demo。

这使 AI 成为体验增强能力，而不是游戏能否运行的硬依赖。

## 五、技术方案

### 1. 技术栈

- Godot 4.x
- GDScript
- Web 导出
- JSON 数据驱动
- GitHub Pages 公网 Demo

### 2. 内容与运行时分层

项目遵循：

> 人读 Markdown，运行时消费 JSON。

Markdown 用于：

- 剧本
- 分镜
- 角色设定
- 线索卡
- 制作规格
- 历史审校

JSON 用于：

- 场景节点
- 对白
- 选择
- 状态变量
- 条件
- 效果
- 结局路由

当前第一章包含：

- 14 个稳定 `scene_id`
- 线索收集状态
- 普通人和军中信任值
- 提问次数与问题类型
- 介入倾向
- 知识债务
- 三种结局条件

内容、系统和美术资源可以独立迭代，降低后续扩展成本。

## 六、适配知乎社区的场景价值

### 1. 让“阅读内容”变成可参与体验

知乎的内容通常以问题、回答和讨论展开。本项目把文章阅读转化为：

- 可进入的文章世界
- 可调查的证据空间
- 可追问的 AI 回答
- 可承担后果的选择

它展示了知乎内容从图文形态进入互动叙事和游戏体验的可能性。

### 2. 保留知乎的问题文化

项目不把知乎当作单纯的品牌装饰，而是保留其核心表达方式：

- 从问题开始
- 鼓励主动追问
- 允许不同答案并存
- 通过证据形成判断
- 让玩家在回答前先理解上下文

最终结局也不是系统宣布唯一正确答案，而是让玩家看到自己的选择如何改变局部历史。

### 3. 发挥刘看山的社区角色

刘看山在游戏里承担“问题连接器”的功能：

- 帮玩家理解复杂背景
- 把历史知识转成可行动线索
- 在玩家卡住时降低进入门槛
- 用反问保留玩家自己的判断空间

这比单纯让刘看山作为装饰角色出现，更符合其作为知乎社区引导形象的定位。

### 4. 形成可持续的内容扩展方式

项目未来可以扩展为：

- 历史问题章节
- 科普问题章节
- 社会议题互动故事
- 用户问题改编的短篇关卡
- 社区共创的多结局时间线

统一的 JSON 内容契约可以让不同主题共享同一套场景、问答、线索和结局系统。

### 5. 具备天然的分享和讨论属性

每个玩家都可能得到不同结局，并可以围绕以下问题展开讨论：

- 你选择介入还是旁观？
- 你认为哪条证据最重要？
- 改变历史是否一定代表更好的结果？
- 如果是你，你会把消息交给谁？

这类差异化结果适合形成知乎式的复盘、回答和二次讨论。

## 八、项目价值总结

《这真的是对的时间线吗？》尝试回答一个具体的产品问题：

> 知乎上的一个问题，能不能从“被阅读的内容”变成“被亲自经历的世界”？

项目用游戏提供行动，用 AI 提供引导，用知乎的问题文化提供叙事起点，再用历史时间线和多结局让玩家承担自己的判断。

它的核心价值不是把文章做成游戏，而是让玩家在阅读、提问、调查和选择中真正经历一次：

> 从知道问题，到愿意回答问题。
